1) WHAT THIS SYSTEM DOES
------------------------

This project runs a full hotspot internet business stack:

- MikroTik router runs the captive portal and controls internet access.
- FreeRADIUS + MySQL (radius DB) stores users, passwords, session/accounting, quotas, and policy groups.
- PHP services handle signup, OTP, password changes, wallet, plan purchase, admin actions, health checks, alerts, and automation.
- CoA disconnects force users to re-auth so new policy/quota applies immediately.
- NetFlow collection provides traffic forensics/audit exports.

In short:
- Captive portal gets users online.
- Pay portal handles money and plans.
- RADIUS enforces policy.
- Scripts + cron keep enforcement/health running.

3) CORE ARCHITECTURE (HOW COMPONENTS CONNECT)
----------------------------------------------

A) USER PATH

1. Device joins Wi-Fi.
2. MikroTik redirects HTTP to hotspot login page (hotspot/login.html).
3. User can:
   - Login (existing account)
   - Signup (new user) with OTP
   - Go to pay portal to buy data
4. RADIUS auth accepts/rejects login.
5. Router assigns address-list/rate policy from RADIUS reply.
6. User gets internet according to policy.

B) BILLING PATH

1. User logs into pay portal (pay-portal/login.php).
2. Wallet is credited from approved payment.
3. User buys plan (purchase.php).
4. Plan attributes are written to RADIUS tables:
   - expiry
   - quota
   - speed/rate
   - active group/address-list
5. CoA disconnect is sent so router re-applies new policy instantly.

C) ENFORCEMENT PATH

1. Accounting updates usage into radacct.
2. Usage/expiry checked by:
   - realtime status logic
   - nister_quota_enforce.sh
3. If expired/exhausted/unpaid, user is moved to limited or nopaid policy.
4. Optional CoA kick enforces immediately.

D) OBSERVABILITY PATH

1. health_check cron writes health samples/events.
2. tunnel_watchdog timer monitors route/ping and recovers tunnel.
3. radacct_cleanup timer closes stale/duplicate sessions.
4. NetFlow collector stores flow files for forensic exports.

5) USER ACCOUNT + AUTH BEHAVIOR
-------------------------------

Phone number normalization:
- Canonical user key is normalized MSISDN.
- System handles both login variants:
  - local form: 0XXXXXXXXX
  - intl form: 233XXXXXXXXX

Signup:
- Endpoint: api/hotspot/signup.php
- Requires valid OTP signup token.
- Writes both username variants into RADIUS.
- Sets:
  - Cleartext-Password
  - Expiration (long default for unpaid account)
  - Simultaneous-Use = 3
  - initial address list/group to unpaid policy

Login:
- Portal login checks supported password formats from radcheck.
- Successful login regenerates session and updates stored user location context.
- Login rate limiting exists per IP and per IP+user.

Session cap / password sharing:
- Simultaneous-Use is enforced as 3.
- Both username variants are synced so 0/233 mismatch does not bypass limits.

9) BILLING + PAYMENTS FLOW
--------------------------

Normal path:

1. User requests top-up (deposit_request.php) -> payments row status=pending.
2. Admin approves in dashboard/API.
3. Approval credits accounts + ledger entry.
4. User buys plan from wallet.
5. purchase.php:
   - checks/sanitizes plan + location
   - acquires per-user lock
   - prevents duplicate near-time purchases
   - debits wallet
   - inserts purchase record
   - applies plan to RADIUS
   - attempts CoA disconnect
   - marks purchase applied
6. SMS templates can notify pending/approved/declined/purchase.

Idempotency and safety:
- Ledger ref uniqueness + DB locks avoid duplicate credits/debits.
- Transaction safety path can mark purchase state/refund if plan-apply fails.


10) PLAN ENFORCEMENT LOGIC
--------------------------

Where plan data comes from:
- Global catalog: RADIUS group attrs (radgroupreply/radgroupcheck)
- Optional per-location override: location_plans

When a plan is applied:
- Expiration written in radcheck.
- Simultaneous-Use enforced.
- Quota attrs written (Nister-Quota-Bytes + MikroTik hi/lo total limit attrs).
- Plan metadata attrs written (plan code/name/duration/window-start).
- HS_LIMITED / HS_NOPAID removed.
- HS_ACTIVE ensured.
- Address list/rate limit set.

Usage accounting:
- Used bytes are computed from radacct using both upload and download octets
  (input + output, including gigawords), with overlap-aware window math.

Policy states:
- HS_ACTIVE -> paid/active browsing.
- HS_LIMITED -> limited path.
- HS_NOPAID -> unpaid/no paid access.


11) WHAT HAPPENS FOR EACH USER TYPE
-----------------------------------

New user:
- Must OTP-verify and sign up.
- Starts as unpaid policy until purchase.

Existing paid user:
- Login accepted if password + policy valid.
- Internet allowed while not expired/exhausted/limited.

Existing user with expired plan:
- Marked expired from status logic.
- Enforcement scripts can move to limited/nopaid and kick.

Existing user with exhausted data:
- Marked exhausted from usage vs quota.
- Enforcement moves to limited state and can disconnect.

Existing user with no purchase:
- Remains unpaid policy (HS_NOPAID).

Password sharing:
- Simultaneous-Use = 3 limits concurrent sessions.
- Accounting tracks sessions in radacct (subject to accounting availability).

If RADIUS is down:
- New auth and policy refresh are impacted.
- Existing active sessions may continue until disconnect/reauth.
- Accounting quality depends on router + radius accounting backup behavior.

20) SECURITY MODEL
------------------

Implemented controls:

- Separate user/admin sessions.
- HttpOnly cookies + SameSite settings.
- CSRF check for admin mutating requests.
- Bearer token protection for admin decision/pending and legacy endpoints.
- Optional token for non-browser hotspot status API callers (HOTSPOT_STATUS_TOKEN);
  trusted hotspot browser origins are allowed so the static MikroTik status page can verify users.
- Origin checks on hotspot OTP endpoints and hotspot status API.
- Request rate limiting for login/password-change/status endpoints.
- Trusted proxy CIDR handling for real client IP extraction.
- Shell usage uses validation + escaping for CoA/script paths.

Operational caution:
- Keep secrets only in secure env/config files.
- Do not expose legacy endpoints unless absolutely required.
- Rotate secrets and verify both router and server are updated together.

25) TROUBLESHOOTING MATRIX
--------------------------

Symptom: User paid but still no internet
- Check purchase status in DB.
- Check user group/address-list in radusergroup/radreply.
- Check CoA ACK/NAK logs.
- Force disconnect and retry login.

Symptom: Only one plan visible
- Check global plan definitions in radgroupreply/radgroupcheck.
- Check location_plans override rows.
- Check user/site location resolution.
- Check plans endpoint output for user location.

Symptom: OTP not sending
- Check HOTSPOT_OTP_ALLOWED_ORIGINS.
- Check SMS gateway settings (MNOTIFY_* or provider base).
- Check OTP rate limit thresholds.

Symptom: Health shows tunnel fail
- Verify route device matches required device(s).
- Verify ping target reachable.
- Check tunnel watchdog and VPN services.

Symptom: Accounting gaps
- Check router RADIUS accounting backup behavior and timeout settings.
- Check radacct cleanup activity.
- Check whether sessions are closing/stopping correctly.
